$ARGUMENTS 의 PRD 를 읽고, 코드를 쓰기 전에 설계 산출물을 만든다. CLAUDE.md 와 docs/adr 의 기존 결정을 먼저 읽고 충돌하지 않게 한다.

## 1. 이벤트 스토밍 (표로)
- 커맨드 → 애그리게이트 → 도메인 이벤트 → 정책(이벤트가 촉발하는 다음 커맨드) 흐름
- 각 애그리게이트의 **불변식**(항상 참이어야 하는 규칙)과 그 불변식을 지키는 트랜잭션 경계
- 어느 서비스(바운디드 컨텍스트)가 소유하는지. 기존 4개 서비스 중 어디인지, 새 서비스가 필요한지 근거와 함께

## 2. 실패 시나리오
- 각 서비스 경계에서: 중복 전달 / 역순 도착 / 응답 유실(결과 불명) / 부분 실패 시 어떻게 되는가
- 보상 방법과 멱등 키

## 3. API 명세 초안
- `docs/api/<service>.yaml` 에 추가할 경로를 OpenAPI 3.0 으로 작성 (Idempotency-Key, 202 비동기, RFC 9457 problem type 포함)
- 새 problem type 은 명세 상단 표에 추가

## 4. 데이터 모델
- 테이블/인덱스 초안. **예상 핫 쿼리마다** 어떤 인덱스로 어떤 실행계획이 나와야 하는지 적는다(→ QueryPlanRegressionTest 항목)

## 5. 태스크 분해
- 1개 PR = 1개 수직 슬라이스. 각 태스크에 "완료 조건(테스트)" 과 상대 크기(S/M/L)
- 먼저 해야 하는 결정이 있으면 ADR 후보로 분리

산출물은 대화에 먼저 보여주고, 승인받은 뒤 파일로 쓴다.
