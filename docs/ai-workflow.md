# AI-Driven Development — 이 프로젝트를 만든 방식

이 저장소는 **Claude Code 를 설계부터 구현·테스트·성능 분석·문서화까지 전 과정에 사용해** 만들었다.
AI 를 "코드 자동완성" 이 아니라 **설계 파트너 + 구현자 + 리뷰어** 로 쓰되, 결과물은 테스트와 측정으로만 신뢰한다는 원칙을 지켰다.
아래는 그 과정과, 팀에서 재사용할 수 있게 저장소에 남긴 장치들이다.

## 1. 흐름: PRD → 설계 → 태스크 → 구현 → 검증 → 문서

| 단계 | 사람이 한 일 | AI 가 한 일 | 저장소에 남은 것 |
|---|---|---|---|
| 문제 정의 | 경쟁 프로젝트 조사 결과로 "흔한 주제(재고 차감·선착순 쿠폰) 대신 **픽업 약속**" 을 핵심 문제로 결정 | 유사 오픈소스(시간대별 주문 건수 제한, FIFO 큐)의 한계를 정리 | `docs/prd/pickup-promise.md` |
| 설계 | 트레이드오프 최종 결정 | 이벤트 스토밍, 불변식, 실패 시나리오 표, API 초안 | `docs/adr/*`, `docs/api/order-service.yaml`, `/prd-to-design` |
| 구현 | 경계·규칙 정의(CLAUDE.md) | 모듈 단위 구현, 테스트 동시 작성 | `CLAUDE.md`, 훅 |
| 검증 | 실패 원인 판단 | 테스트 실행 → 실패 분석 → 수정 루프 | JVM 94개 + Python 19개 테스트, n8n · K8s 배포 검증, CI |
| 성능 | 측정 설계, 결과 해석 | 부하 스크립트·쿼리 실험 작성, 구간별 지연 분해 | `docs/performance/*`, `scripts/query-lab`, `load-test/` |
| 리뷰 | 최종 승인 | 규칙 기반 셀프 리뷰, PR 리뷰 자동화 | `/review`, `claude-review.yml`, 서브에이전트 |

## 2. AI 결과물을 믿지 않고 검증한 장치

AI 가 만든 코드는 그럴듯해 보이는 것이 가장 위험하다. 그래서 "사람이 읽고 납득" 대신 **기계가 실패시키는** 장치를 먼저 깔았다.

- **불변식 테스트**: "슬롯 초과 예약 0", "포인트 지갑 잔액 = lot 합 = 원장 합", "정산 지급액 = 순매출 − 수수료(DB CHECK)"
- **실행계획 회귀 테스트**: "인덱스를 탈 것이다" 라는 AI 의 주장을 `EXPLAIN` 결과로 단언
- **API 드리프트 테스트**: 설계 명세와 구현이 어긋나면 빌드 실패
- **ArchUnit**: 도메인 계층이 프레임워크를 모르는지
- **E2E**: 5개 서비스를 실제 Kafka 로 연결해 돈의 흐름과 고객 알림까지 검증

## 3. 반복 개선 사례 — AI 결과물을 분석하고 고친 기록

실제로 이 루프에서 잡힌 것들이다. (AI 가 처음부터 맞힌 것보다, 틀린 것을 **어떻게 발견했는지**가 중요하다.)

1. **E2E 가 설계 가정의 오류를 잡음**: "PG 타임아웃 → Saga 타임아웃" 시나리오 테스트가 실패했다. 원인은 코드 버그가 아니라
   결제 복구 주기(1s)가 Saga 타임아웃(4s)보다 빨라 **정상적으로 결제 완료**된 것. 테스트 조건을 운영 설정 관계(복구 유예 > Saga 타임아웃)와
   맞추고, 두 설정의 관계를 문서화했다.
2. **실행계획 테스트가 "항상 인덱스 순서 스캔" 이라는 가정을 반박**: 주문 20건 회원은 플래너가 `Bitmap Scan + Sort` 를 골랐고,
   이는 합리적이었다. 단언을 "헤비 유저에서 Sort 가 없어야 한다" 로 바꿔 데이터 분포를 테스트 설계에 반영했다.
3. **plan-doctor 오탐 수정**: `LIMIT` 아래 노드는 조기 종료되므로 "예상 30,860행 vs 실제 21행" 은 통계 오류가 아니다.
   규칙에 "LIMIT 하위 노드 제외" 를 추가하고, 실제 회귀 테스트가 만든 실행계획을 테스트 픽스처로 고정했다.
4. **부하 테스트로 Kafka 소비자 병목 발견**: 결제 Saga p95 13.7s. 주문 DB 와 결제 DB 의 타임스탬프를 조인해 구간을 쪼개 보니
   "명령 소비 대기" 가 원인 → 리스너 동시성 1 → 3. 결제 처리량 2배에서 p95 0.46s. (docs/performance/load-test.md)
5. **의존성 충돌**: swagger-parser(javax)와 springdoc(jakarta) 충돌로 `/v3/api-docs` 가 500. 스택트레이스로 원인을 찾고
   파서를 Jackson YAML 로 교체.
6. **셀프 리뷰로 잠금 순서 결함 발견**: 테스트는 모두 통과했지만 `/review` 체크리스트(동시성 → 잠금 순서)로 전 경로의 잠금 순서를 표로 정리하자,
   Saga 타임아웃 잡만 "Saga 행 → 주문 행" 순서로 잠가 응답 처리("주문 행 → Saga 행")와 엇갈렸다. 타임아웃 경계에서만 드물게 나는
   교착상태라 테스트로는 잡히지 않는 종류다. 후보 조회를 비잠금으로 바꾸고 건별 트랜잭션에서 주문 행부터 잠그도록 수정했다.
7. **스스로 정한 규칙 위반을 커밋 전에 되돌림**: 쿠폰 기능을 넣으면서 이미 커밋된 정산 V1 마이그레이션의 주석을 고쳤다. "커밋된 마이그레이션은 불변"
   (Flyway 체크섬이 바뀌어 기존 DB 가 기동 실패) 규칙에 걸려 즉시 되돌리고 V2 로 분리했다. 훅이 Claude Code 도구 경로의 수정을 막지만,
   스크립트로 파일을 바꾸는 경로는 훅을 거치지 않아 리뷰로 잡았다. 그래서 같은 규칙을 CI 에도 넣었다(`scripts/check-migrations.sh`,
   수정·삭제된 V*.sql 이 있으면 빌드 실패).

## 4. 팀이 재사용할 수 있는 장치 (`.claude/`)

| 종류 | 이름 | 용도 |
|---|---|---|
| 프로젝트 메모리 | `CLAUDE.md` | 구조, 명령, **반드시 지킬 규칙 10개**, 테스트 관례 |
| 커맨드 | `/prd-to-design` | PRD → 이벤트 스토밍 · 불변식 · 실패 시나리오 · OpenAPI 초안 · 태스크 분해 |
| 커맨드 | `/review` | 변경분을 메시징·동시성·Saga·돈·DB·API·계층 체크리스트로 리뷰 |
| 커맨드 | `/explain-plan` | 실행계획 회귀 테스트 → plan-doctor → 근거 기반 개선안 |
| 커맨드 | `/new-event`, `/adr` | 이벤트 추가 절차, ADR 작성 규칙 |
| 서브에이전트 | `saga-failure-analyst` | 중복·역순·결과 불명·늦은 응답 등 7가지 장애 유형 표 + 재현 테스트 |
| 서브에이전트 | `ddd-reviewer`, `query-plan-analyst` | 애그리게이트 경계 / 실행계획 리뷰 |
| 훅 | `guard-migrations.sh` | **커밋된 Flyway 마이그레이션 수정을 차단** (AI 가 "고치기 쉬운" 기존 파일을 건드리는 실수 방지) |
| 훅 | `format-kotlin.sh` | 편집한 모듈만 ktlintFormat |
| CI | `claude-review.yml` | PR 마다 규칙 기반 자동 리뷰 (ANTHROPIC_API_KEY 등록 시) |
| 도구 | `tools/plan-doctor` | 실행계획 규칙 진단(CI 게이트) + `--ai` 로 Claude 리뷰 (스키마 포함, 프롬프트 캐싱) |

## 5. 원칙

- AI 에게 맡길수록 **검증 장치를 먼저** 만든다. 테스트가 없는 영역은 AI 산출물을 머지하지 않는다.
- 수치는 측정한 것만 쓴다. 문서의 모든 성능 수치는 재현 스크립트가 있다.
- 결정은 사람이 하고, ADR 에 "기각한 대안과 이유" 를 남긴다. AI 는 대안을 넓게 펼치는 데 쓴다.
