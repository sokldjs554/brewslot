# PRD — 픽업 약속(Pickup Promise)

> 이 문서는 `/prd-to-design` 커맨드(.claude/commands)의 입력이 된 원본 요구사항이다.
> 도메인 모델·API·태스크 분해는 이 문서로부터 AI 와 함께 도출했고, 결정 사항은 docs/adr 에 남겼다.

## 1. 문제

- 스마트오더 사용자는 "매장 상황에 따른 예상 수령시간" 이 아니라 **내가 원하는 시각**에 받기를 원한다.
- 출근 시간대(07:30~09:30)에는 인기 시각에 주문이 몰려 매장 제조 능력을 넘기고, **약속한 시각에 음료가 준비되지 않는다.**
- 결과: 매장 앞 대기, 식은 커피·녹은 얼음, 점주 클레임 대응, 재주문율 하락.

## 2. 목표 / 지표

| 지표 | 정의 | 목표 |
|---|---|---|
| 약속 준수율 | 약속 시각까지 READY 된 주문 비율 | 95% 이상 |
| 초과 예약 | 슬롯 용량을 넘는 주문 수락 건수 | 0 |
| 대안 전환율 | 409 응답 후 제안 시각으로 주문한 비율 | 측정 시작 |
| 결제 완료 시간 | 결제 시작 → 주문 확정 p95 | 1초 이하 |
| 재주문 소요 | 지난 주문 재주문까지 탭 수 | 3 탭 이하 |

## 3. 사용자 스토리

1. 고객은 장바구니 기준으로 **받을 수 있는 시각과 혼잡도**를 본다.
2. 고객은 원하는 시각을 고르고, 불가능하면 **가장 가까운 대안 시각**을 제안받는다.
3. 고객은 포인트와 카드를 섞어 결제한다. 결제가 실패하면 차감된 포인트는 자동으로 돌아온다.
4. 바리스타는 픽업 순서가 아니라 **"지금 만들어야 할 음료"** 순서로 제조 큐를 본다.
5. 점주는 스테이션별 용량(바리스타 결근, 머신 고장)을 조정한다. **이미 받은 주문은 지켜진다.**
6. 점주는 매일 정산서(카드·포인트 매출, 수수료, 지급액)를 받고, 플랫폼은 PG 파일과 대사한다.
7. 고객은 지난 주문을 한 번에 재주문한다. 품절·가격 변경·가장 빠른 픽업 시각이 미리 계산돼 있다.

## 4. 비기능 요구사항

- 러시아워 조회 트래픽이 주문 처리(잠금)와 경합하지 않을 것
- 메시지 유실·중복·역순 전달에도 돈(카드·포인트·정산)이 틀어지지 않을 것
- PG 응답 유실(결과 불명) 시에도 고객 돈이 묶이지 않을 것
- 모든 오류는 클라이언트가 분기 가능한 `type` 을 가질 것 (RFC 9457)

## 5. 범위 밖
