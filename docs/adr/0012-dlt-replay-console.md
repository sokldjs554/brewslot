# ADR-0012. DLT 재처리를 도구로: FastAPI 콘솔 + n8n 알림

- 상태: 채택
- 관련 코드: `services/dlt-console`, `automation/n8n`, `infra/datadog/monitors.json`

## 맥락

Kafka 소비에 계속 실패한 메시지는 재시도 후 `<topic>.DLT` 로 격리된다(ADR-0003). 격리 자체는 안전하지만 **자동 복구되지 않는
유일한 경로**라, 사람이 원인을 고친 뒤 다시 흘려보내야 한다. 이 작업을 kafka-console 명령으로 손으로 하면
어느 메시지를 이미 재처리했는지 남지 않고, 같은 메시지를 두 번 보내기 쉽다.

## 결정

1. **읽기는 소비자 그룹 없이.** 콘솔이 DLT 를 조회해도 서비스의 오프셋에 영향이 없다.
2. **재처리 = 원래 토픽으로 같은 key · value 재발행.** key 가 주문 ID 라 파티션(=순서)이 유지되고,
   소비자 Inbox(ADR-0003)가 같은 eventId 를 한 번만 반영하므로 재처리가 중복돼도 돈이 두 번 움직이지 않는다.
3. **재처리 기록은 compacted 토픽 `ops.dlt-replays`.** 같은 (토픽, 파티션, 오프셋)을 다시 재처리하면 409,
   의도한 경우에만 `force`. 콘솔 자체는 상태를 갖지 않아 재시작·다중 인스턴스에 안전하다.
4. **운영 토큰(`X-Ops-Token`) 필수**, 재처리 건수는 Prometheus 지표로 노출.
5. **알림은 n8n.** Datadog DLT 모니터 → n8n 웹훅 → 콘솔에서 적체 토픽만 골라 Slack 으로 보낸다.
   알림 문구·채널 변경은 워크플로 수정으로 끝나고, 워크플로 JSON 은 저장소에서 CI 로 검증한다.

## 대안

- **자동 재처리(주기적으로 DLT → 원 토픽)**: DLT 에 가는 메시지는 대부분 코드 버그나 계약 불일치라, 원인을 고치기 전에
  다시 보내면 같은 실패가 반복된다. 사람이 원인을 확인한 뒤 재처리하는 흐름을 유지.
- **Kotlin 으로 작성**: 운영 도구는 서비스와 배포 주기가 다르고 작다. Python(FastAPI · aiokafka)으로 가볍게 두고,
  테스트는 FakeBroker 단위 + Testcontainers 실제 Kafka 통합으로 나눴다.
