# ADR-0011. 실시간 주문 알림: WebFlux SSE + 인스턴스별 브로드캐스트 소비

- 상태: 채택
- 관련 코드: `notification-service` (`NotificationHub`, `NotificationController`, `OrderEventListener`, `notification-service.yml`)

## 맥락

고객 앱은 "결제 확정 → 제조 시작 → 준비 완료 → 픽업" 을 폴링 없이 바로 보여줘야 한다. 출근 시간에는 결제를 마친 고객 대부분이
앱을 열어 둔 채 기다리므로, **동시 연결 수가 주문 처리량보다 훨씬 크다.** 요구는 다음과 같다.

1. 연결 하나가 스레드 하나를 붙잡지 않는다.
2. 파드가 여러 개여도 고객 연결이 어느 파드에 붙었는지와 관계없이 알림이 간다.
3. 지하철에서 잠깐 끊겼다 다시 붙으면, 그 사이 알림을 놓치지 않는다.

## 결정

1. **별도 서비스, Spring WebFlux(Netty) + SSE.** 알림은 서버 → 앱 한 방향이라 WebSocket 이 필요 없고, SSE 는 HTTP 그대로라
   프록시·로드밸런서 설정이 단순하다. 기존 서비스(MVC · JDBC)에 섞지 않고 DB 없이 Kafka 만 읽는 서비스로 분리했다.
2. **인스턴스마다 다른 소비자 그룹(`notification-${random.uuid}`), `auto-offset-reset: latest`.**
   같은 그룹이면 이벤트가 파드 하나에만 가서, 연결이 다른 파드에 붙은 고객은 알림을 못 받는다. 브로드캐스트로 받아
   각 파드는 **자기에게 연결된 회원 것만** 내보낸다. 재시작 시 과거 이벤트를 다시 쏟아내지 않도록 latest 부터 읽는다.
3. **회원별 Reactor `Sinks.replay().limit(20)` + `Last-Event-ID`.** 이벤트 ID 는 `"<epochMillis>:<eventId>"` 로 만들어
   정렬 가능하게 했고, 재연결 시 커서 이후 알림만 이어 보낸다. 10분간 구독자가 없는 채널은 정리한다.
4. **연결 직후 코멘트 1건 + 15초 keep-alive.** 헤더를 즉시 flush 해 앱이 "연결됨" 을 알 수 있게 하고,
   유휴 연결을 끊는 프록시(ALB 기본 60초)를 넘긴다.

## 대안

- **같은 소비자 그룹 + Redis Pub/Sub 으로 재분배**: 홉이 하나 늘고 Redis 장애가 알림 장애가 된다. 이벤트 양(주문당 4~5건)이
  작아 모든 파드가 전부 읽어도 부담이 없으므로 기각.
- **기존 order-service 에 SSE 엔드포인트 추가(MVC)**: 연결마다 서블릿 스레드를 점유해 주문 API 스레드 풀과 경쟁한다.

## 결과

- E2E 에서 실제 주문 흐름의 알림 4종을 순서대로 받는 것을, 통합 테스트에서 재연결 이어받기를 검증한다.
- Kubernetes 에서 2개 파드로 띄우고 스모크 테스트가 SSE 로 `OrderPaid` 수신을 확인한다.
- 한계: 파드 재시작 순간 그 파드의 replay 버퍼는 사라진다(앱은 재연결 후 주문 조회 API 로 최종 상태를 맞춘다).
  알림 이력이 필요해지면 Redis Streams 등 공유 저장소로 옮긴다.
