# ADR-0001. 픽업 약속을 제조 부하 기반 백워드 스케줄링으로 지킨다

- 상태: 채택
- 관련 코드: `order-service/.../scheduling/domain/BrewScheduler.kt`, `PickupTimeAdvisor.kt`

## 맥락

사용자는 "매장 상황에 따른 예상 수령시간" 이 아니라 **자신이 고른 시각**에 커피를 받고 싶어 한다.
그런데 출근 시간대에는 인기 시각(08:50 등)에 주문이 몰리고, 매장이 실제로 만들 수 있는 양을 넘기면
"약속한 시각" 은 지켜지지 않는다. 약속이 깨지면 고객은 매장에서 기다리고, 점주는 클레임을 받는다.

흔한 해법과 한계:

| 방식 | 한계 |
|---|---|
| 시간대별 주문 **건수** 제한 (예: 5분당 5건) | 아메리카노 1잔 주문과 스무디 5잔 주문을 같은 1건으로 본다 |
| 매장 전체 대기열(FIFO) + 예상 시간 안내 | 고객이 시각을 고를 수 없다 (서비스 핵심 가치와 충돌) |
| 시간대별 **잔 수** 제한 | 에스프레소 머신은 꽉 찼는데 블렌더는 놀고 있는 상황을 구분 못 한다 |

## 결정

1. **스테이션별 부하(load unit)** 로 용량을 모델링한다. 메뉴마다 `station`(ESPRESSO/BLENDER/BREW_BAR)과 `loadUnits` 를 갖고,
   매장은 스테이션별 "5분 슬롯당 처리 가능 부하" 를 설정한다(바리스타·머신 수 반영).
2. **신선도 창(freshness window)**: 음료는 완성 후 품질이 유지되는 시간이 있다(핫 5분, 아이스 10분).
   픽업 시각 T 의 음료는 `[T - freshness, T)` 구간의 슬롯에서만 만들 수 있다. 한가한 새벽 슬롯에 미리 만들어 두는 비현실적 배정을 막는다.
3. **백워드(JIT) 배정**: 제약이 빡빡한 음료(창이 짧고 부하가 큰 것)부터, 창 안에서 **가장 늦은** 빈 슬롯에 배정한다.
   늦게 만들수록 품질이 좋고, 앞 슬롯을 다음 주문을 위해 남긴다. 한 주문의 음료를 여러 슬롯에 나눠 담을 수 있다.
4. 불가능하면 거절로 끝내지 않고 **가장 가까운 가능 시각 3개**를 제안한다(409 + `alternatives`). 같은 거리면 늦은 시각 우선.
5. 스케줄러는 **순수 함수**(Spring/DB 무의존)로 두고, 동시성은 계획을 DB 에 반영하는 쪽(ADR-0002)이 책임진다.

## 대안

- **최적 배정(정수 계획법)**: 다중 bin-packing 변형으로 NP-hard. 주문당 음료 ≤ 20잔, 창 ≤ 3슬롯 규모에서는
  "tight-first + latest-fit" 탐욕법이 실용적으로 충분하고, 결정적이라 테스트·설명이 쉽다. 반례가 쌓이면 재검토.
- **슬롯 없는 연속 시간 모델**: 정확하지만 동시성 제어(구간 겹침 잠금)가 복잡해진다. 5분 격자는 운영자가 이해하기 쉽다.

## 결과

- (+) 주문 구성에 따라 같은 시각의 가능 여부가 달라진다 → 장바구니 기준 가용 시각 API 제공
- (+) 약속 준수율(`promiseKeptRate`)과 지연 분포(`brewslot.pickup.promise.lateness`)를 측정 → 점주가 용량 설정을 조정하는 근거
- (−) 점주가 메뉴별 부하·신선도를 설정해야 한다 → 기본값 템플릿 제공이 필요 (향후)
- 검증: `BrewSchedulerTest`(12 cases), `PlaceOrderIntegrationTest`, k6 `hot-slot.js`
