# ADR-0013. 매장 변경: 새 자리를 먼저 잡고, 수락하는 순간 한 트랜잭션에서 옮긴다

- 상태: 채택
- 관련 코드: `order-service` (`StoreTransferService`, `StoreTransfer`, `MenuEquivalence`, `StoreAlternatives`, `JdbcCapacityLedger.handOver`, `V3__store_transfer.sql`),
  `settlement-service` (`TRANSFER_OUT/IN`), `loyalty-service` (`STORE_TRANSFER`), `payment-service` (`RefundPayment.storeId`)

## 맥락

원하는 시각에 픽업한다는 약속은 주문 순간(ADR-0001)뿐 아니라 **결제 후** 에도 깨질 수 있다. 바리스타가 빠지거나 머신이 멈추면
매장이 밀리고, 고객은 "같은 브랜드 근처 매장에서 받고 싶다" 고 한다. 흔한 처리 — 취소하고 다시 주문 — 는 세 가지 문제가 있다.

1. 취소 후 재주문 사이에 새 매장 자리가 사라지면 고객은 **주문도 자리도 잃는다.**
2. 쿠폰은 결제 중 만료될 수 있고(ADR-0010), 환불 · 재결제 동안 카드 한도가 이중으로 잡힌다.
3. 정산 · 포인트 원장에서 취소와 새 주문이 따로 기록돼 "한 잔" 이 두 거래로 남는다.

## 결정

1. **원래 주문을 먼저 건드리지 않는다.** 요청 시 새 매장 자리를 **transfer ID 를 예약 키로** 잡는다(HELD).
   이때 원래 매장 자리 · 결제 · 쿠폰 · 포인트는 그대로다.
2. **새 매장이 수락하는 트랜잭션 하나에서 옮긴다.** 원래 자리 해제 → 새 자리를 주문 ID 로 넘기며 CONFIRMED →
   주문의 매장 · 항목(새 매장 메뉴 ID) · 약속 시각 변경 → `OrderTransferred` (Outbox). 도중에 실패하면 전부 롤백된다.
3. **실패는 모두 "원래 주문 유지" 로 끝난다.** 새 매장 거절(`REFUSED`), 기한(기본 2분) 무응답(`EXPIRED`),
   원래 매장이 먼저 제조 시작 · 고객 취소(`ABORTED`) — 어느 쪽이든 새 자리만 풀고 `OrderTransferFailed` 로 알린다.
4. **경합은 주문 행 잠금으로 판정한다.** 수락 · 거절 · 만료 · 원래 매장 제조 시작 · 취소 모든 경로의 잠금 순서는
   "주문 행 → transfer 행 → 슬롯 행(스테이션 · 시각 순)" 으로 고정했다(ADR-0005 에서 겪은 교착상태 교훈).
   DB 부분 유니크 인덱스로 **진행 중인 요청은 주문당 하나, 완료된 변경은 주문당 한 번** 을 보장한다.
5. **같은 음료 · 같은 가격일 때만 옮긴다.** 메뉴 ID 는 매장마다 다르므로 이름 · 가격 · 판매 여부로 대조한다(`MenuEquivalence`).
   결제 금액이 그대로여야 카드 · 포인트 · 쿠폰을 다시 건드리지 않는다. 안 되는 이유는 음료 이름으로 돌려준다.
6. **돈의 귀속만 옮긴다.**
   - 정산: `TRANSFER_OUT`(원래 매장, −총액, −카드 수수료) / `TRANSFER_IN`(새 매장, +총액, +카드 수수료). PG 거래와 대사(카드 행)는 그대로.
   - 포인트 원장: `store:{원래}:clearing → store:{새}:clearing` 분개(`STORE_TRANSFER`).
   - 이후 환불 · 사용 취소 명령에 **현재 매장** 을 담아 보낸다(`RefundPayment.storeId`, `ReverseRedemption.storeId`, 하위 호환 필드).
     이 분개들은 서로 교환 가능해, Kafka 토픽 간 도착 순서와 관계없이 최종 잔액이 같다.
7. **재시도는 같은 결과.** 고객 요청은 `Idempotency-Key`, 새 매장 수락은 "이미 COMPLETED 면 그대로 반환" 이라
   응답을 못 받은 앱 · 태블릿이 다시 눌러도 두 번 옮겨지지 않는다. 상태는 `GET /orders/{id}/transfers/{transferId}` 로 다시 확인한다.
8. **주문 시에도 같은 규칙을 쓴다.** 원하는 시각이 꽉 차 409 를 줄 때, 같은 브랜드 매장 중 **그 시각 그대로** 되는 곳을
   그 매장 메뉴 ID 로 바꾼 장바구니와 함께 `nearbyStores` 로 돌려준다.

## 대안

- **취소 후 재주문**: 위 맥락의 세 문제. 가장 단순하지만 고객이 주문을 잃을 수 있는 유일한 방식이라 기각.
- **새 매장 수락 없이 즉시 이동**: 용량 원장만 보면 가능하지만, 실제 매장은 재료 · 인력 사정으로 거절할 수 있다.
  수락 단계와 기한을 두는 대신, 수락 전에도 원래 주문이 살아 있게 했다.
- **차액 결제 · 부분 환불 지원**: 가격이 다른 매장으로도 옮길 수 있지만 결제 Saga 를 한 번 더 돌려야 한다. 범위 밖으로 두고,
  가격이 다르면 이유(`PRICE_DIFFERS`)를 알려 준다.

## 결과

- 통합 테스트 8건: 수락 · 거절 · 만료 · 원래 매장 선착수 · **수락과 제조 시작 동시 도착 8회 반복(한쪽만 이기고 용량 누수 0)** ·
  멱등 · 메뉴 불일치 · 주문 시 근처 매장 제안. E2E: 쿠폰+포인트+카드 주문을 옮겨 픽업, 옮긴 뒤 취소 → 새 매장 기준 환불,
  정산서에서 원래 매장 −13,500 / 새 매장 +13,500 · 카드 수수료도 이동.
- 한계: 매장 변경은 주문당 한 번. 원래 매장 매출 통계(CQRS)는 변경 시각의 영업일에서 뺀다(결제와 변경이 날짜를 넘기면 하루 어긋날 수 있음).
