# ADR-0010. 쿠폰 이벤트(프로모션)

- 상태: 채택
- 관련 코드: `loyalty-service` (`CouponService`, `PointService.redeem`, `V2__coupon_promotion.sql`), `order-service` (`Order.couponAmount`, `CheckoutSaga`), `settlement-service` (`COUPON_SALE`)

## 맥락

주문 · 결제 · 적립 · 정산에 더해 브랜드 **이벤트(프로모션)** 도메인이 필요하다. 요구는 세 가지다.

1. "오픈 기념 1,000원 쿠폰 선착순 100명" 같은 이벤트에서 **한도를 절대 넘겨 발급하지 않는다.**
2. 결제 시 쿠폰과 포인트를 함께 쓰고, 결제가 실패하면 **둘 다** 정확히 되돌린다.
3. 할인 비용을 누가 부담하는지가 정산에 드러나야 한다(매장이 할인만큼 손해 보지 않는다).

## 결정

1. **선착순 발급 = "쿠폰 행 INSERT(회원당 1장) → 캠페인 재고 조건부 UPDATE" 를 한 트랜잭션으로.**
   `UPDATE coupon_campaign SET issued_count = issued_count + 1 WHERE id = ? AND issued_count < issue_limit` 는 행 잠금 후
   조건을 다시 평가하므로 동시 요청이 몰려도 한도를 넘지 않는다. 재고가 없으면 예외로 롤백해 쿠폰 행도 남기지 않는다.
   같은 회원의 재요청은 `(campaign_id, member_id)` 유니크로 같은 쿠폰을 돌려준다(멱등).
2. **쿠폰과 포인트는 loyalty-service 의 로컬 트랜잭션 하나로 사용한다.** 둘 다 같은 DB 에 있으므로 Saga 단계를 늘리지 않는다.
   모든 검사(쿠폰 소유·상태·만료·금액·최소 주문액, 포인트 잔액)를 끝낸 뒤에 쓰기를 시작해, 한쪽만 쓰인 상태가 생기지 않는다.
   잠금 순서는 항상 지갑 → 쿠폰(보상도 동일).
3. **할인액은 "고객이 본 금액" 을 주문에 기록하고, 결제 단계에서 loyalty-service 가 검증한다.**
   order-service 가 주문 순간 loyalty-service 를 동기 호출하지 않아도 되고(서비스 간 통신은 Kafka 뿐이라는 원칙 유지),
   조작되거나 그 사이 바뀐 금액은 `COUPON_AMOUNT_MISMATCH` 로 거절돼 주문이 `COUPON_REJECTED` 로 취소된다.
4. **할인 비용은 브랜드 부담.** 분개: 차) `brand:{b}:promotion` / 대) `store:{s}:clearing`. 매장은 정가 기준으로 정산받고,
   정산서에 `couponSales` / `couponReversals` 가 따로 보인다.
5. **보상 시 쿠폰 복원 정책:** 유효기간이 남았으면 `ISSUED`(다시 사용 가능), 결제 중에 지났으면 `EXPIRED`.
   유효기간을 임의로 연장하지 않는다(연장은 CS 운영 정책으로 별도 처리).

## 기각한 대안

- **쿠폰을 별도 Saga 단계로 분리**: 같은 DB 의 두 자원을 굳이 분산 트랜잭션으로 만든다. 보상 경로와 타임아웃 조합만 늘어난다.
- **주문 시 order-service → loyalty-service 동기 조회**: 결합도와 장애 전파(loyalty 가 느리면 주문도 느려짐)가 생긴다.
  검증 시점을 결제 단계로 미뤄도 잘못된 금액은 돈이 움직이기 전에 걸러진다.
- **Redis 로 선착순 재고 차감**: 쿠폰 행과 재고가 다른 저장소에 있으면 한쪽만 반영되는 경우의 복구 기준이 모호하다(ADR-0002 와 같은 이유).

## 결과

- (+) 선착순 10장 이벤트에 50명 동시 요청 → 정확히 10장, 실패 요청의 쿠폰 행 0건 (`CouponIntegrationTest`)
- (+) 같은 쿠폰으로 두 주문이 동시에 결제해도 한 주문만 사용
- (+) 카드 거절 시 쿠폰·포인트가 함께 복원, 할인액 조작 요청은 주문 취소 — 4개 서비스 E2E 로 검증
- (−) 쿠폰 거절은 결제 버튼을 누른 뒤에야 알 수 있다. 화면은 쿠폰함 조회 결과로 미리 걸러 보여 주고, 서버 검증은 최후 방어선으로 둔다.
