# ADR-0005. 결제 Saga: Orchestration, 포인트 → 카드 순서, 멱등 보상

- 상태: 채택
- 관련 코드: `CheckoutSagaOrchestrator.kt`, `CheckoutSaga.kt`, `PaymentService.kt`, `PointService.kt`

## 맥락

한 번의 결제가 세 서비스(주문 슬롯, 포인트, 카드)에 걸친다. 분산 트랜잭션(2PC)은 PG 같은 외부 시스템과 불가능하다.

## 결정

1. **Orchestration**: order-service 가 `checkout_saga` 테이블에 진행 상태를 저장하고 명령을 발행한다.
   흐름이 한 곳에 보이고, 타임아웃·보상을 한 곳에서 판단할 수 있다(Choreography 는 흐름이 이벤트 구독에 흩어진다).
2. **순서: 포인트 차감 → 카드 결제**. 포인트 부족은 흔하고 되돌리기 싸다. 카드 승인 취소는 드물지만 비싸다(망취소, 고객 알림).
   실패 확률이 높고 보상 비용이 낮은 단계를 앞에 둔다.
3. **보상 명령은 멱등**: `RefundPayment`/`ReverseRedemption` 은 "했으면 되돌리고, 안 했으면 무시". 그래서 결과를 모르는
   상황(타임아웃)에서도 **가능한 모든 보상을 안전하게** 보낼 수 있다.
4. **순서 보장**: 같은 주문의 명령은 key=orderId → 같은 파티션. "차감 → 차감취소" 가 역전되지 않는다.
5. **결과를 모르는 결제(PG 타임아웃)**: payment-service 는 PG 호출을 DB 트랜잭션 밖에서 하고, 응답을 못 받으면 `UNKNOWN` 으로 둔 뒤
   복구 잡이 PG 거래 조회로 확정한다. 그사이 도착한 환불 명령은 "환불 예약" 으로 기록해 두었다가 승인이 확인되는 즉시 취소한다.
6. 오케스트레이터 핸들러는 **"도메인 검증(예외 가능) → 부수효과(Outbox)"** 순서를 지킨다. 중복·역순 응답을 무시하고 커밋할 때
   부수효과가 반쯤 기록되는 것을 막는다.

## 실패 시나리오 표 (모두 테스트로 고정)

| 시나리오 | 결과 | 테스트 |
|---|---|---|
| 포인트 부족 | 카드 결제 시도 없이 취소, 슬롯 반환 | `CheckoutSagaIntegrationTest` |
| 카드 거절 | 포인트 복원 명령, 취소 | Saga IT, E2E |
| PG 타임아웃 → Saga 타임아웃 → 늦은 승인 | 주문 취소, 늦은 승인은 자동 취소, 포인트 복원 | Payment IT, E2E |
| 같은 응답 중복 전달 | Inbox 가 흡수, 1회 반영 | Saga IT |
| 결제 후 매장 거절 | 환불 + 포인트 복원 + 슬롯 반환 | Saga IT |
| 결제 요청 더블 클릭 | 같은 Saga 반환 | Saga IT |
