# ADR-0002. 슬롯 용량의 동시성 제어: 정렬된 행 잠금

- 상태: 채택
- 관련 코드: `JdbcCapacityLedger.kt`, `PlaceOrderService.kt`, `V1__order_schema.sql (slot_capacity)`

## 맥락

인기 시각에는 수십 명이 같은 슬롯 행을 동시에 갱신한다. 한 주문이 **여러 슬롯 행**(스테이션 × 시각)을 한꺼번에 점유해야 하고,
하나라도 모자라면 전부 취소돼야 한다(원자성). 초과 예약은 곧 "지켜지지 않는 약속" 이다.

## 결정

1. 용량의 원천(source of truth)은 **PostgreSQL `slot_capacity`** 행이다.
2. 필요한 슬롯 행은 **별도 짧은 트랜잭션**에서 `INSERT .. ON CONFLICT DO NOTHING` 으로 미리 만든다.
   (본 트랜잭션에서 INSERT 경합이 섞이면 잠금 순서를 통제하기 어렵다.)
3. 본 트랜잭션은 `ORDER BY station, slot_start FOR UPDATE` 로 **모든 요청이 같은 순서로** 행을 잠근다 → 교착상태 불가능.
4. 잠근 뒤 잔여 용량을 재확인한다. 계획 이후 다른 주문에 밀렸으면 `SlotRaceLostException` → **새 트랜잭션에서 재계획**(최대 3회).
   같은 트랜잭션에서 재시도하지 않는 이유: 이미 잡은 잠금과 새 계획의 잠금 순서가 어긋날 수 있다.
5. 최후 방어선: `CHECK (reserved <= capacity)`.
6. 점유는 `HELD`(결제 전, TTL 5분) → `CONFIRMED`(결제 완료) → `RELEASED`(취소/만료). HELD 도 용량을 차지한다(좌석 선점 모델).

## 대안

| 대안 | 기각 이유 |
|---|---|
| Redis Lua 로 원자적 다중 키 차감 | 빠르지만 용량이 Redis 와 DB 에 **이중 기록**된다. Redis 장애/유실 시 복구 기준이 모호하고, 주문 저장과 원자적으로 묶을 수 없다 |
| 낙관적 잠금(version) + 재시도 | 인기 슬롯에서는 충돌률이 높아 재시도 폭주. 비관적 잠금이 오히려 처리량이 안정적이다 |
| `SERIALIZABLE` 격리수준 | 직렬화 실패 재시도를 전 경로에 넣어야 하고, 어떤 쿼리가 충돌하는지 예측이 어렵다 |
| 슬롯별 단일 스레드 큐(액터) | 인스턴스 간 라우팅(샤딩)이 필요 — 현재 규모에서 과한 복잡도 |

## 결과

- (+) 40명 동시 주문 테스트, k6 100명 동시 주문에서 **정확히 이론값만 수락, 초과 예약 0**
- (+) 슬롯 원장 `reserved` = 살아있는 예약 라인 합 — 부하 테스트 후 불일치 0건 확인
- (−) 같은 슬롯의 주문은 직렬화된다. k6 hot-slot 에서 100건 p95 194ms. 슬롯당 초당 수백 건 이상이 필요해지면
  "슬롯을 N개 서브 버킷으로 쪼개 잠금 분산" 을 검토한다.
- 조회(가용 시각) 트래픽은 잠금과 분리한다 → ADR-0004
